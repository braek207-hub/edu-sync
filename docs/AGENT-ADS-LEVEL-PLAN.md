### Дефект, который витрина закрывает первым: `own_keyword` защищает не то

B1 закрыл несовпадение единицы (запрет пишется в кампанию, защита считалась по
кабинету) и оставил открытым «спящий ключ». Замер показал, что дыра шире и
другого рода.

`objects.core_words_by_campaign` (`objects.py:326`) и
`objects.bought_phrases_by_campaign` (`objects.py:371`) считают «что мы купили»
по колонке `matched_key` витрины запросов, а это `Criteria` отчёта
SEARCH_QUERY_PERFORMANCE_REPORT (`segments.py:493-520`). Разбор последнего окна:

```
строк в окне                                        37 318
из них matched_key совпадает с самим запросом       32 266  (86,5 %)
пар (кампания, matched_key) всего                   34 569
  где matched_key ≠ query:  2 303, из них есть ключом в кабинете  1 948 (84,6 %)
  где matched_key = query: 32 266, из них есть ключом в кабинете     532 ( 1,6 %)
```

То есть 31 734 строки, которые защита считает «нашей купленной семантикой», —
это пользовательские запросы, подобранные автотаргетингом, а не ключи. Когда
`Criteria` действительно отличается от запроса, это настоящий ключ с
операторами («+колледж +синергия», «сайт колледжа -подмосковье») и он находится
в кабинете в 84,6 % случаев.

Отсюда и цифра B1 «2156 слов из 2163 сняты защитой»: защита строилась на
множестве, в котором 98,4 % элементов ключами не являются.

**Правильный источник «что мы купили» уже лежит в базе.** 110 534 пары
(кампания, ключ) без автотаргетинга, у каждой есть `parent_id` — группа. Из них
108 203 (97,9 %) в отчёте запросов последнего окна не видны вовсе: это и есть
«спящий ключ», названный в B1 как открытый вопрос.

Отдельно: 129 017 ключей покрывают 129 кампаний, а объявления и группы — 139.
Десять кампаний без единого ключа — это автотаргетинговые и, вероятно, ЕПК;
разбирается на Этапе 2, потому что для них «своя семантика» определяется иначе.

## Что берётся из bjorn-синка

`sync/bjorn/sync_ads.py` — единственный работающий в репозитории синк
статистики уровня объявления. 946 строк за 27 дней, 49 объявлений, 35 строк в
день, 272 кБ.

**Переносится:**

| Что | Откуда | Почему именно так |
|---|---|---|
| Состав полей отчёта `Date, CampaignId, AdGroupId, AdId, Impressions, Clicks, Cost` | `sync_ads.py:55-66` | проверено пробами 5–7 и 12, `IncludeVAT: YES` — НДС уже внутри, ×1,2 не применять |
| `CampaignIds` чанками по 10 | `sync_ads.py:68` | одиннадцатая кампания роняет весь вызов; ровно тот же лимит уже стоит в `segments.py:35` |
| Свёртка строк отчёта по ключу «день + AdId» с суммированием | `sync_ads.py:131-161` | отчёт отдаёт несколько строк на одну пару |
| Фильтр «только объявления с показами за период» | `sync_ads.py:213-220` | без него приезжает архив: проба 6 дала 755 картинок против 48 работавших объявлений |
| Разбор блоков `*AdFieldNames` | `sync_ads.py:82-88` | `ads.get` отвергает `TextAd` в `FieldNames` ошибкой 8000 |

**Не переносится, и почему:**

* **Транспорт записи.** bjorn пишет через PostgREST (`bjorn/common.py:283`,
  `SupabaseRest.upsert`), агент — через psycopg батчами (`agent/db.py::_batch`).
  Смешивать нельзя: у агента таблицы создаются DDL-списком в том же модуле, а
  гейт данных считает строки прямым SQL.
* **Метрика на объявление** (`sync_ads.py:163-211`, `ym:s:lastsignDirectBanner`).
  У агента поведение живёт на уровне кампании (`edu_agent_behavior`,
  `agent/db.py:157`), и решения по нему не принимаются — это ранний сигнал
  качества. Тянуть его на 37 972 объявления значит платить квотой Метрики за
  измерение, которого ни один генератор не спрашивает. Заводится, когда
  появится потребитель, — не раньше.
* **Справочник объявлений** (`sync_ads.py:213-330`: `adimages.get`,
  `creatives.get`, `preview_url`). У EDU все 61 209 объявлений — `TEXT_AD`,
  картинок и креативов нет вовсе. Справочник уже есть в `edu_agent_objects`.
* **Дневная грань.** У bjorn 49 объявлений; у EDU 35 588. См. расчёт объёма
  ниже — дневная грань здесь стоит больше, чем вся нынешняя база.
* **`ads.get` целиком.** `segments.fetch_objects` делает то же самое, с
  параллелизмом по чанкам (`segments.py:481-488`, `OBJECT_WORKERS = 4`) и с
  версионированием по хешу. Второй читатель того же API — второй источник
  правды о структуре.

## Этап 1. Витрина статистики групп и объявлений

**Граница:** только чтение. Ни одного нового рычага, ни одной правки
генераторов. Новая таблица и её наполнение тактом Э0.

**Критерий готовности:** на прод-данных отвечается вопрос «сколько денег и
конверсий принесло каждое объявление и каждая группа за неделю», и ответ
сходится с `edu_agent_facts` по кампании до рубля на осевших днях (тот же
критерий, что у гейта сумм, `agent/gate.py`, `SUM_SETTLE_DAYS = 1`).

### Схема витрины

Грань — **неделя**, по прецеденту `sync/agent/slices.py:1-13`: корректировки
считаются за окно целиком, дневная динамика ловится на уровне кампании в
`edu_agent_facts`. Расчёт цены дневной грани — в разделе «Объём» ниже.

```sql
CREATE TABLE IF NOT EXISTS edu_agent_ad_facts (
  week_start    DATE NOT NULL,       -- slices.to_week_start(Date отчёта)
  campaign_id   TEXT NOT NULL,       -- CampaignId отчёта
  adgroup_id    TEXT NOT NULL,       -- AdGroupId отчёта
  ad_id         TEXT NOT NULL,       -- AdId отчёта
  cost          DOUBLE PRECISION NOT NULL DEFAULT 0,   -- Cost, IncludeVAT=YES
  clicks        INTEGER NOT NULL DEFAULT 0,            -- Clicks
  impressions   INTEGER NOT NULL DEFAULT 0,            -- Impressions
  conversions   INTEGER NOT NULL DEFAULT 0,            -- Conversions_<цель>_<атрибуция>
  PRIMARY KEY (week_start, campaign_id, adgroup_id, ad_id)
)
```

Гранулярность и ключ:

* **Ключ полный, а не только `ad_id`.** Объявление принадлежит ровно одной
  группе, но адрес нужен целиком: генератор спрашивает «что в этой группе», а
  не «где живёт это объявление», и джойн за родителем в `edu_agent_objects` на
  каждый вопрос стоил бы сканирования 241 МБ.
* **Статистика группы не хранится отдельно.** В поиске каждый показ
  принадлежит объявлению, поэтому сумма по `adgroup_id` и есть статистика
  группы. Вторая таблица была бы вторым источником правды о тех же деньгах.
* **Колонки `conversions`.** Имя колонки в ответе — `Conversions_<цель>_<модель>`,
  а не `Conversions`; берётся `segments.primary_goal_column`
  (`segments.py:197`), как у срезов и запросов. Кабинет, чей отчёт не отдал ни
  одной колонки конверсий, из витрины исключается целиком и называется в
  отчёте прогона — по тому же доводу, что `blind_accounts` в
  `agent_e0.py:1096-1103`: ноль конверсий у всех объявлений означает «конверсии
  не спрошены», а не «объявления бесполезны».
* **`campaign_name`, `direction`, `project` не дублируются.** Они живут в
  `edu_agent_facts` и соединяются по `campaign_id`.

Фильтр строк — **клики больше нуля**. Не показы: объявление с показами и без
кликов не несёт ни решения, ни денег, а строк порождает столько же. Это тот же
довод, по которому `fetch_search_queries` (`segments.py:502-506`) отбирает
только строки с кликами.

### Объём и чем платим

Верхняя граница без фильтра: 35 588 объявлений в состоянии `ON` внутри
кампаний с расходом.

| Вариант | Строк | При 294 Б/строку |
|---|---|---|
| Дневная грань, все объявления | 35 588/день | 10,5 МБ/день, **315 МБ/мес** |
| Недельная грань, все объявления | 35 588/нед | 10,5 МБ/нед, **545 МБ/год** |
| Недельная грань, только с кликами | *измеряется первым прогоном* | см. бюджет |

Дневная грань за квартал (≈ 945 МБ) превышает всю нынешнюю
`edu_agent_objects` (241 МБ) вчетверо и составляет 42 % текущей базы (2236 МБ).
Учитывая инцидент дисковой квоты Supabase (память `supabase-readonly-quota-incident`,
UPDATE у квоты уронил прод), дневная грань здесь не рассматривается.

**Бюджет витрины: 150 МБ в установившемся режиме** — это ≈ 500 000 строк.
Из него выводятся два ограничителя, а не наоборот:

* хранение 26 недель (окно лестницы 90 дней плюс запас на сравнение),
  чистка в `agent/db.py::clear_bulk_tables` (`db.py:1450`) — там уже стоит
  список таблиц массовой перезаписи;
* при 26 неделях бюджет даёт **≤ 19 200 строк на неделю**. Не влезли — хвост
  сворачивается в `ad_id = 'other'` внутри своей группы и недели, механизмом
  `slices.collapse_tail` (`slices.py:47`), порог по кликам подбирается по
  первому замеру, а не назначается заранее.

Предположение, требующее проверки первым прогоном: сколько из 35 588
объявлений получают хотя бы один клик за неделю. Ориентир из bjorn — 35 строк
в день на 49 объявлений (71 %), но там кабинет на два порядка меньше и без
длинного хвоста (медиана EDU — 76 объявлений на кампанию при максимуме 4408).
Если доля окажется выше 54 % (19 200 / 35 588), включается свёртка хвоста.

Цена в API: **одна дополнительная выгрузка CUSTOM_REPORT на кабинет за прогон**
(четыре кабинета). Против нынешней стоимости такта это мало: снимок структуры
уже делает 86 кампаний ÷ 10 на чанк × 3 уровня × страницы по 1000, и именно из-за
него в `segments.py:37-39` заведён `OBJECT_WORKERS = 4` (прогон 31783879686 шёл
35+ минут без параллелизма). Резерв баллов запись не трогает:
`UNITS_RESERVE_SHARE = 0.05` (`writer/apply.py:42`) считается на стороне Э1.

## Этап 2. Связка полного состава

**Граница:** генераторы получают адрес ниже кампании и статистику по нему.
Ни одного нового вида действия. Всё, что агент умеет применять, по-прежнему
адресуется кампанией.

**Критерий готовности:** генератор `proven` умеет сказать «эта группа
окупается, а соседняя в той же кампании — нет», защита `own_keyword` считается
по ключам кабинета, а не по `Criteria` отчёта, и отчёт прогона называет число
снятых кандидатов до и после.

### Полное произведение не строится, и вот число

B4 формулирует цель как «связка = кампания × группа × объявление × сегмент ×
запрос». Полное произведение этих измерений построено не будет, по тому же
доводу, по которому оно уже отвергнуто этажом выше (`slices.py:1-13`: «полное
произведение за 90 дней — 17,6 млн комбинаций»).

Счёт на живых числах: 22 679 групп × 13 демографических ключей (3 устройства +
3 пола + 7 возрастов) = 294 827 строк на неделю **до того, как добавлен хотя
бы один запрос**. Запросов сейчас 37 318 строк на окно на 86 кампаний — 434 на
кампанию; с разрезом по группам множитель неизвестен и измеряется пробой.

Вместо произведения — **адрес плюс независимые двумерные срезы**, как уже
сделано на уровне кампании:

| Измерение | Где живёт | Состояние |
|---|---|---|
| адрес: кампания, группа, объявление | `edu_agent_objects` + `edu_agent_ad_facts` | Этап 1 |
| объявление × неделя (деньги, клики, конверсии) | `edu_agent_ad_facts` | Этап 1 |
| группа × ключ (что куплено) | `edu_agent_objects`, `object_level='keyword'`, `parent_id` | **уже есть** |
| группа × запрос (что пришло) | `edu_agent_search_queries` + `adgroup_id` | требует пробы |
| сегмент (device/gender/age/region) | `edu_agent_facts_sliced`, уровень кампании | не меняется |
| текст объявления | `edu_agent_objects`, `payload->'TextAd'` | **уже есть** |

Сегмент остаётся на кампании сознательно: корректировка ставки на уровне
группы у API есть (`bidmodifiers` принимает `AdGroupId`), но рычага у агента
нет, а измерение без рычага — это строки в базе и ноль решений.

### Проба, от которой зависит третья строка таблицы

Принимает ли SEARCH_QUERY_PERFORMANCE_REPORT поле `AdGroupId` — в репозитории
не проверено ни разу. У CUSTOM_REPORT оно работает (bjorn), у отчёта запросов
это другой перечень полей, и угадывать здесь уже стоило восьми упавших
прогонов в соседнем месте (`segments.py:402-410`). Проба ставится отдельным
запуском `probe_report_fields.py` с переключателем типа отчёта, до правки схемы.

Исход пробы меняет форму работы:

* **принимает** — в `edu_agent_search_queries` добавляется колонка `adgroup_id`
  и первичный ключ становится `(window_from, campaign_id, adgroup_id, query)`.
  Это миграция таблицы на 349 350 строк и 140 МБ, и она умножает строки:
  запрос, купленный в трёх группах кампании, станет тремя строками. Отсечка
  `top_queries_by_cost` (`objects.py:56`, 500 строк на кампанию) при этом
  перестаёт значить прежнее и пересчитывается по замеру;
* **не принимает** — группа у запроса восстанавливается джойном по паре
  (кампания, `Criteria`) к снимку ключей: 84,6 % пар с настоящим ключом
  находятся в кабинете. Для оставшихся адрес группы неизвестен и обязан быть
  `NULL`, а не подставлен ближайшим — на этом и построен нынешний дефект.

### Починка `own_keyword` — главная ценность этапа

Замер выше: 98,4 % того, что защита считает «своей купленной фразой», ключом
кабинета не является. Правка:

* `objects.core_words_by_campaign` (`:326`) и
  `objects.bought_phrases_by_campaign` (`:371`) меняют вход с «строки отчёта
  запросов» на «ключи кабинета из снимка»: 110 534 пары (кампания, ключ),
  включая 108 203 спящих, которых отчёт не видит вовсе;
* автотаргетинговый псевдоключ `---autotargeting` (16 721 строка) в защиту не
  входит: он не фраза и запретить его минус-словом нельзя. Кампании, где
  трафик идёт только автотаргетингом, получают свою причину в отчёте, а не
  пустое множество, читаемое как «мы ничего не покупали»;
* десять кампаний с объявлениями, но без единого ключа, разбираются отдельно и
  называются в отчёте прогона — молчаливое «своей семантики нет» у них
  означало бы разрешение минусовать что угодно.

Ожидаемый эффект (предположение, проверяется прогоном): часть из 2156 слов,
снятых защитой на замере B1, снова становится видимой. Точное число до правки
неизвестно и назначаться не должно.

## Этап 3. Рычаги уровня объявления

**Граница:** ровно два новых вида действия — пауза и снятие паузы объявления.
Правка текстов в этот этап не входит (см. «Чего этот план НЕ делает»).

**Критерий готовности:** агент умеет поставить на паузу объявление, которое
проигрывает соседнему в своей группе, откатить это одним действием, и никогда
не может выключить последнее показывающееся объявление группы.

### Почему пауза, а не правка

B4 говорит: «allow-лист агента их не получает: удаление объектов запрещено, а
правка текста это пересоздание». Первая половина верна буквально
(`guardrails.py:143-163`: всё со словом delete/remove отбивается, исключение
одно — `negative.remove_added`), вторая — по существу, но не по API.

`ads.update` у Директа существует и текст менять умеет. Цена в другом:
`writer/switch.py:144` фиксирует различие, на котором всё держится — «Status
описывает модерацию, State — показы». Правка текста возвращает объявление в
модерацию, показы прерываются, и история объявления как объекта замера
разрывается: «до и после» сравнивает два разных объявления под одним `Id`.
Замер такта против заповедника (задача 25 мастер-плана) на таком объекте не
работает вовсе.

`ads.suspend` / `ads.resume` — другое дело. Это пауза, а не удаление, то есть
ровно та форма, которую рельса уже разрешает («агент только паузит»,
`guardrails.py:141`), и `apply._RESULT_COLLECTION` уже знает коллекции
`SuspendResults` и `ResumeResults` (`apply.py:111-113`). Откат — обратный вид,
возврат в известное прошлое состояние.

### Рельса, которой сегодня нет и которая обязана появиться

61 209 объявлений на 32 330 групп — **1,89 объявления на группу**. Значит есть
группы с одним объявлением, и пауза в них останавливает не объявление, а
группу целиком: то же самое, что `campaign.suspend`, но мимо своей полосы
(`LANE_SUSPEND`), мимо своего капа (`max_suspends_per_run`) и мимо кулдауна.

Рельса: **действие отбивается, если в группе не останется ни одного
объявления в состоянии `State = ON`**. Считается по `edu_agent_objects`
(снимок структуры уже есть), а не по формуле построителя — как и все прочие
рельсы, которые обязаны считать сами (`guardrails.py:83-86`, довод про минус-фразы).

Вторая рельса: **число пауз объявлений за прогон** — свой предел, не общий с
кампаниями. Кампаний 86, объявлений 37 972; общий счётчик означал бы, что один
прогон вправе выключить сколько угодно объявлений, пока не тронул кампании.

## Чего этот план НЕ делает

* **Не правит тексты объявлений.** Ни `ads.update`, ни генерации заголовков.
  Правка возвращает объявление в модерацию и разрывает историю замера
  (`switch.py:144`); новое объявление — наряд билдеру, а наряд у билдера
  сегодня умеет три вида (`build_order.py:46`: consolidate, rebuild, expand) и
  ни одного «дописать объявление в существующую группу». Это правка контракта
  в двух репозиториях (`docs/BUILD-ORDER-CONTRACT.md`, `builder/order.py`) —
  отдельная задача с собственным планом, как и требует правило.
* **Не заводит корректировки на уровне группы.** API умеет, рычага у агента
  нет; измерение без рычага — строки в базе и ноль решений.
* **Не трогает стратегии как измерение.** B4 упоминает их вместе с
  объявлениями, но стратегия — поле кампании, оно уже в
  `edu_agent_settings_snapshot`, и рычаг `strategy.set` уже в allow-листе.
  Отдельной витрины здесь не нужно.
* **Не тянет Метрику на объявление.** Потребителя нет; появится — заводится
  тогда, по образцу `bjorn/sync_ads.py:163`.
* **Не строит полное произведение измерений.** Причина и число — в Этапе 2.
* **Не добавляет ни одного экрана в Panda-BI.** Карта агента читает манифест,
  манифест строится из тех же констант, которыми живёт агент.
* **Не включает `--apply` для новых видов.** Порядок выпуска — лестница
  автономии, она уже подключена и работает без деплоя через `lane_steps`.
* **Не чинит дефекты блока A.** Этот план исполняется после них.

## Порядок

1. **Проба полей отчёта** — до любой схемы. Один запуск, один кабинет.
2. **Этап 1** — витрина статистики. Не зависит ни от чего, кроме пробы.
   Не меняет ни одного решения агента, поэтому едет параллельно блоку A.
3. **Замер объёма после первой недели** — гейт: не влезли в бюджет, включается
   свёртка хвоста и замер повторяется. Дальше не идём.
4. **Этап 2** — только после A6 (`--apply` на кроне) и после недели с зелёным
   Этапом 1. Внутри: сначала защита по ключам, потом адрес в связке.
5. **Этап 3** — после первой недели, где действия, посчитанные по группам,
   применялись и разбирались.

Суммарно по плану: **34 файла, 1 система, 1 новая таблица, 1 миграция
существующей** (условно, по исходу пробы). Разбито на три этапа так, что ни
один в отдельности не выходит за правило `scope-explosion`, а первый ничего не
ломает, даже если два следующих не будут сделаны.
