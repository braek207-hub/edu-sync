# Агент-директолог EDU — план реализации

Живой документ. Правится по мере прохождения этапов; отменённые решения не стираются,
а помечаются с причиной — иначе через месяц никто не вспомнит, почему сделали не так.

## 1. Цель

**Контракт месяца** (как KPI ставится снаружи): на плановый месяц выдаются
план по лидам, бюджет B и план по выручке = 2×B. Выручка меряется **когортой** —
это оплаты лидов, ПРИШЕДШИХ в плановый месяц, когда бы они ни заплатили.
Не касса месяца. Следствия:

- при лаге оплаты p50=5, p90=33, p99=137 дней на конец месяца видна лишь часть
  выручки когорты → факт по выручке требует **прогноза дозревания**, иначе месяц
  всегда выглядит проваленным, а решения внутри месяца слепы;
- внутренняя цель механизма — `Прибыль = Выручка(расход) − расход → max` при
  освоении бюджета. B — **план освоения, а не потолок** (уточнение Павла 22.08):
  недотрата = невыполнение (недополученные лиды и выручка), реализовать нужно
  весь бюджет — вопрос только В ЧТО. Оптимизация — не «тратить ли», а
  «куда именно», чтобы прибыль на этом объёме была максимально возможной.
  Если после освоения предельный рубль всё ещё окупается с запасом — агент
  говорит «дайте больше» с расчётом ожидаемой отдачи.

Два KPI кабинета, в порядке приоритета:

1. **План по эффективным лидам за выделенный бюджет.** Первично.
2. **ROMI.** Пол — 0 % (самоокупаемость, выручка = расход). Цель — 100 % (выручка ×2).

Постановка задачи, в которой это живёт:

- бюджет осваивается целиком; распределение — по выравниванию предельной отдачи;
- максимизируем эффективные лиды при ROMI ≥ 0 %;
- остаток бюджета после выполнения плана идёт туда, где выше отдача, — к ROMI 100 %;
- **пол по ROMI держится на уровне КАБИНЕТА, а не каждой кампании.** Отдельная кампания
  может быть убыточной, если нужна для объёма, пока портфель в целом держит пол;
- **красная линия:** если план достижим только уходом ниже самоокупаемости, агент
  останавливается на границе и показывает разрыв. Такое решение принимает человек.

Конфликт критериев осознан: план по лидам легко нагнать дешёвым трафиком, который хуже
оплачивает, — и ROMI просядет. Односторонний оптимизатор ломает второй KPI. Поэтому
объём — цель, окупаемость — ограничение, и они разведены по разным уровням решений.

**Автономия** (уточнение Павла 22.08): агент — полноценный директолог, а не
советчик. Решения в рамках бюджета — его: считает, применяет, ставит
эксперименты, читает их результат и корректирует себя. Человеку остаются три
случая: красная линия выше (конфликт заданных снаружи KPI), запрос бюджета
сверх B и необратимые действия, пока класс уверенности (Э2.3) не заработал.
Каждое решение — с записанным ожиданием («жду +N лидов к дате D»), чтобы сторож
мог судить решение, а не только откатывать по риску.

## 1.1. Контур принятия решения — как работает целиком

Такт: **неделя** на решения, **день** на надзор. Один цикл:

1. **Видеть** (Э0, крон). Факты по кампаниям, срезы, запросы, снапшоты настроек,
   квазиэксперименты. Гейт качества данных: RED → цикл не считается вовсе.
2. **Оценить состояние.** Лестница воронки даёт каждому объекту рабочую метрику
   и ожидаемые оплаты/выручку ± ошибка (Э2.1). Когортная экономика по
   направлениям. Декомпозиция разрыва план/факт по множителям — по владельцам,
   с поправкой на дозревание (§6).
3. **Сгенерировать кандидатов** — по уровням, из таблицы рычагов (§7):
   портфель (двинуть бюджет к порогу предельной цены), кампания (бюджет,
   статус), внутри кампании (корректировки, расписание, минус-слова, ставки).
4. **Оценить каждого кандидата.** Ожидаемый эффект в деньгах — через лестницу и
   кривую насыщения. Уверенность — из четырёх источников (§3). Класс действия —
   по цене ошибки × обратимости (Э2.3).
5. **Решить.** `P(лучше) × выигрыш > P(хуже) × потеря`, порог зависит от класса.
   Недельный риск-бюджет ограничивает сумму поставленного на кон; заповедник
   (holdout) не трогается — это контрольная группа.
6. **Применить** (движок Э1a). Guardrails, журнал действий, и у КАЖДОГО действия —
   записанное ожидание: «жду Δ метрики к дате D». Действие без ожидания не
   применяется: его нечем будет судить.
7. **Следить** (сторож, ежедневно). Факт против ожидания; выход за нижнюю
   границу → автоматический откат; исход действия — в журнал экспериментов.
8. **Учиться.** Закрытые действия пополняют историю квазиэкспериментов (Э2.4),
   приоры пулинга уточняются, пороги пересчитываются. Неделя закрывается
   отчётом: что сделал, почему, что вышло, где разрыв и чей он. Часть бюджета
   решений — эксперименты агента по собственным гипотезам (Э5, бандиты):
   исследование — не роскошь, а единственный источник кривых насыщения там,
   где история молчит.

Состояния действия: `посчитано → решено → применено → наблюдается → закрыто
(подтвердилось / не подтвердилось / откачено)`. Всё в журнале, ничего в голове.

## 2. Почему «статистическая значимость» — неверная рамка

Из 83 кампаний кабинета порог значимости не проходит **ни одна** (прогон 32581633972:
`pass_decision_threshold: 0`, `pass_ab_threshold: 7`). При ~450 оплатах в год классический
A/B не заработает никогда.

Значимость нужна, чтобы публиковать статью. Нам нужно решать с деньгами и обратимостью:

> действуем, если `P(лучше) × выигрыш > P(хуже) × потеря`

У корректировки ставки цена ошибки — тысячи рублей и один запрос отката. У отключения
кампании — потерянный поток на недели плюс потеря обучения стратегии. Порог уверенности
у них обязан быть **разный**, а не общий.

## 3. Откуда берётся уверенность, когда данных «нет»

Четыре независимых источника. Ни один сам по себе не достаточен, вместе — хватает.

**3.1. Суррогат вместо редкого события.** Оплата — событие с базой ~1.4 %. У каждого лида
есть `p_pay` от ML-модели: 100 лидов дают 100 непрерывных чисел вместо одной-двух
бинарных оплат. Требует доказательства пригодности — см. этап Э2.0.

**3.2. Спуск по воронке.** `оплаты → сделки → соединения → эффективные лиды → лиды`.
Берём самую глубокую ступень, где событий хватает, и пересчитываем через исторический
коэффициент перехода. Сами переходы (% соединения, % сделки, цена ступени) становятся
управляемыми метриками — данных на них в разы больше.

**3.3. Пулинг у похожих.** Объект занимает статистику не у «среднего по кабинету», а у
похожих на себя (направление, профиль успеха, расстояние до профиля). Чем больше своих
данных — тем меньше занимает. Механизм сжатия уже есть (`computed.py::shrink_ratio`),
нужен второй уровень приора.

**3.4. История уже оплачена.** 194 квазиэксперимента в `edu_agent_experiments` (DiD по
скачкам бюджета) не читает никто. Каждое прошлое изменение — эксперимент, который уже
провели и за который уже заплатили.

## 4. Уровни решений — их нельзя смешивать

| Уровень | Вопрос | Данные | Отвечает за |
|---|---|---|---|
| Кабинет | какой срез работает вообще | много | пороги, общие правила |
| Направление | куда переложить деньги | средне | **ROMI** (чек и конверсия в оплату) |
| Кампания | сколько дать и дать ли | мало | объём, предельная цена |
| Группа / ключ | что внутри жжёт впустую | очень мало | цена эффективного лида |

Два KPI ложатся на разные уровни: **план по лидам** двигают ставки, время, сегменты,
минус-слова (кампания и ниже); **ROMI** двигает микс направлений (портфельный уровень) —
перекладывание бюджета между направлениями меняет его сильнее любой корректировки ставки.

Сегментные корректировки (возраст, пол, устройство) считаются **по кабинету** и применяются
ко всем кампаниям — это дефект, см. Э2.2. Покампанийные срезы собираются только по трём
измерениям: регион, сеть, устройство. По полу и возрасту покампанийных данных нет вовсе.

## 5. Портфельный уровень: единый порог вместо ручных бюджетов

Решение о бюджете принимается по **предельной** отдаче — цене следующего лида, а не по
среднему CPA кампании. У кампании есть насыщение: до какого-то объёма рубль дешёвый,
дальше дорожает. «Лучшая по CPA» часто уже уперлась, и доливать надо не в неё.

Форма решения — не «этой +30 %, той −20 %», а **один порог предельной цены эффективного
лида на кабинет**. Каждая кампания берёт столько, сколько освоит, не перейдя порог. Порог
двигается, пока сумма по кабинету не сойдётся с планом. Тогда:

- **отключение кампании** = «даже первый рубль дороже порога», а не волевое решение;
- **увеличение бюджета** = «предельный рубль всё ещё дешевле порога».

**Каннибализация.** Кампании не независимы: брендовые и общие пересекаются по спросу.
Эффект портфельных решений проверяется на уровне кабинета (сумма сошлась), а не по частям.

## 6. Декомпозиция разрыва

Выручка когорты — произведение, и разрыв раскладывается по множителям точно,
а не «на глаз»:

```
Выручка = Расход × (1/CPL) × p_eff × p_conn × p_deal × p_pay × Чек
          трафик   трафик     трафик  продажи  продажи  продажи  продукт/микс
```

Вклад каждого множителя в разрыв — через логарифмы: `log(факт/план)` по
множителям суммируется в `log(разрыв)` без остатка (точное разложение, порядок
множителей не важен). Доля множителя = его лог-вклад / лог-разрыв. Свойства:

- **Аддитивность:** вклады складываются в 100 % разрыва — «повесить всё на
  трафик» арифметически не выйдет.
- **Владельцы:** CPL и p_eff — агент (трафик); p_conn, p_deal — отдел продаж
  (скорость обработки, дозвон); чек — микс направлений, то есть портфельное
  решение агента. Разрыв печатается ПО ВЛАДЕЛЬЦАМ.
- **План множителей:** плановые значения — из зрелой истории (точка отсчёта
  выше), а не из ожиданий. Смещение множителя против своей истории — сигнал
  и промежуточная цель со своим рычагом.
- **Незрелость ≠ разрыв:** внутри месяца факт сравнивается с планом только
  после поправки на профиль дозревания (88 % за 30 дней) — иначе первые недели
  всегда «провалены».

Замер 22.08 подтвердил и обратную сторону: множители реально различаются по
направлениям (чек 73–174 тыс., p_pay 6.1–25 %) — значит, декомпозиция без
разреза по направлениям спрячет главный рычаг.

## 7. Рычаги: что агент умеет и чего нет

| Рычаг | Состояние | Обратимость |
|---|---|---|
| Корректировки ставок (пол, возраст, устройство) | **работает** | высокая |
| Расписание показов | **работает** | высокая |
| Региональные корректировки | **мертво**: срез отдаёт `TargetingLocationName`, API записи требует числовой `RegionId` | высокая |
| Минус-слова | считаются, применять нечем | средняя |
| Ставки ключей | нет | высокая |
| Ключи вкл/выкл | нет | высокая |
| Бюджеты кампаний | нет | высокая |
| Кампании вкл/выкл | нет | **низкая** (теряется обучение стратегии) |
| Объявления и группы | нет | средняя |
| Автотаргетинг: категории + бренд-опции | читаем (снимок настроек: `params.autotargeting.categories`); запись — `keywords.update` → `AutotargetingSettings` (API с 21.11.2023): Categories EXACT/ALTERNATIVE/COMPETITOR/BROADER/ACCESSORY + BrandOptions без брендов / свой бренд / бренды конкурентов | высокая |

Единая валюта любого рычага — **ожидаемая прибыль** (постановка Павла 23.08):
корректировки, сплит бюджетов, запуски/отключения, минус-слова, категории
автотаргетинга, гео — всё оценивается через лестницу (Э2.1) с поправкой на
качество сегмента (Э2.2b), а не через «лидов стало больше». Больше лидов при
худшем соединении/оплате — это минус, и механизм обязан его видеть.

## 8. Этапы

Каждый этап заканчивается **гейтом** — фактом из данных, а не мнением. Не прошёл гейт —
следующий этап не начинается.

### Готово

- **Э0** — фундамент: факты, срезы, объекты, запросы, квазиэксперименты, вычисляемые
  настройки, профиль, мощность. По крону, зелёный.
- **Э1a** — движок записи: корректировки ставок и расписание, недельный риск-бюджет,
  журнал действий, сторож с откатом. Первая боевая запись сделана (прогон 32583007883:
  3 действия по кампании 114057545, ограничитель `max_campaigns=1`).

### Э2 — механизм принятия решений

- **Э2.0. Пригодность ML-суррогата.** Померить на истории, насколько **сумма `p_pay` по
  группе** предсказывает фактические оплаты этой группы. Это НЕ то, что мерили раньше:
  AP 0.05 говорит о плохом ранжировании отдельных лидов, а решения строятся на агрегатной
  калибровке — модель может быть слабой поштучно и пригодной в агрегате, и наоборот.
  **Гейт:** агрегатная ошибка предсказания оплат по группам приемлема на отложенном
  периоде. Не прошёл — `p_pay` из механизма решений исключается, работаем на воронке.
  **Итог (22.08, прогон 32586391429): гейт НЕ пройден для портфельного уровня.**
  Поштучно p_pay работает (AUC 0.702 при базе 1.6 %), но по кампаниям точнее наивной
  оценки «лиды × база» лишь на 11–14 %, а по направлениям — **хуже наивной на 23 %**.
  Систематический недобор 16 % (total_bias 0.84). Решения по деньгам строятся на
  воронке (Э2.1); p_pay остаётся только вспомогательным сигналом внутри кампании.
- **Э2.1. Лестница воронки.** Выбор целевой метрики по объёму событий объекта, с
  пересчётом через исторические коэффициенты перехода. Убирает жёсткий порог
  `sum_p_pay ≥ 25`, из-за которого сегодня решений нет ни по одному объекту.
  **Сделано (22.08, `sync/agent/ladder.py`, прогон 32592039259):** порог = 25
  событий ЛЮБОЙ ступени (тот же смысл — 20 % ошибки счётчика); коэффициенты —
  пул направления с откатом на кабинет, weak-пометка ненадёжных; у оценки явная
  относительная ошибка √(1/n + Σ1/n_коэфф). На бою: рабочую ступень получили
  **169 объектов из 176** (paid 6 · deals 57 · connected 31 · eff 31 · leads 11
  · clicks 33), медианная ошибка 0.13–0.22, weak-коэффициентов ноль. Окно
  сдвинуто на p90 лага оплаты из данных прогона (30 дн). Без ступени — 7
  объектов-пустышек (битые UTM `{campaign_id}`, ручной `vuz`, замершие кампании).
- **Э2.2. Уровень расчёта.** Иерархия «кабинет → направление → кампания» с частичным
  пулингом вместо одной кабинетной цифры на все кампании. **Блокирует снятие
  `max_campaigns=1`:** пока не сделано, расширять раскатку нельзя.
  **Расчёт сделан (22.08, `sync/agent/hierarchy.py`):** двухшаговый пулинг для
  device (единственный срез с рабочим рычагом; region мёртв, network — не
  корректировка), вес приора от базы родителя, `pool_weight` в каждой строке,
  запись под `object_level='campaign'`. Движок записи пока читает кабинетный
  уровень — переключение применения на «кампания, если есть, иначе кабинет» +
  снятие ограничителя — отдельный шаг после сверки дельт на бою.
  **Боевой прогон 32594265050:** 106 кампаний получили личные значения
  (233 строки, отказов 0). Дельты против кабинетной цифры — до **76 п.п. с
  переворотом знака** (кабинет account10 держит TABLET −38 %, а кампания
  710178257 заслуживает +38 %). Это и есть измеренная цена раскатки одной
  цифры на всех — ограничитель стоял не зря.
- **Э2.2b. Качество лида сегмента (вопрос Павла: «а % соединения?»). СДЕЛАНО
  (23.08, `sync/agent/segment_quality.py`).** Конверсия клик→лид — половина
  правды: сегмент может давать много лидов, которые хуже доходят до денег.
  Замер по мосту `crm_lead_details.client_id × edu_visit_behavior`
  (`probe_device_lead_quality.py`, прогон 32622086445, покрытие 56 % =
  104 254 зрелых лида) подтвердил ровно это:
  - **ПК** p_conn 0.497 · 1625 ₽/лид; **Смартфоны** 0.427 · 1295 ₽;
    **Планшеты** p_conn **0.345** · **792 ₽/лид** — планшетный лид вдвое
    дешевле ПК-шного и на 8–15 п.п. хуже соединяется. Пример «+38 % TABLET»
    из Э2.2 без поправки был бы ошибкой.
  - Паттерн зависит от направления: в med смартфоны ЛУЧШЕ ПК (1520 против
    929 ₽/лид), в spo и dist — наоборот. Значит поправка нужна из данных,
    а не эвристикой «мобилки хуже».
  Механика: device-корректировки (кабинетные и покампанийные) домножаются на
  отношение ожидаемой выручки на лид сегмента к базе моста; редкие глубокие
  ступени сегмента оцениваются той же лестницей Э2.1 (у планшетов мало оплат,
  но тысячи соединений). Обе компоненты — `conv_ratio` и `quality_ratio` —
  остаются в строке и в отчёте прогона. Границы честно записаны: мост — только
  веб-лиды с client_id (56 %), поэтому переносится отношение, не уровень;
  качество пока кабинетное (не по направлениям — на направление × устройство
  глубоких ступеней мало); на уровнях глубже лестница Э2.1 качество видит
  сама — поправка нужна была именно сегментным корректировкам.
- **Э2.3. Шкала уверенности и классы действий.** Единая шкала на объект (свои данные,
  надёжность суррогата, история, согласие похожих) против класса действия по цене ошибки
  и обратимости.
  **Сделано для корректировок (23.08, `sync/agent/confidence.py`):** каждая строка
  расчёта несёт `rel_error` (пуассоновская ошибка отношения, у Э2.2b — сумма
  дисперсий конверсии и качества; колонка в edu_agent_computed_settings, ALTER
  идемпотентный). Решение: p_sign = Φ(|ln ratio|/rel_error) — вероятность, что
  ЗНАК эффекта верен, — против порога класса действия. Пороги (политика, не
  данные): bid_modifier/schedule 0.80 (обратимо, сторож откатит), budget_shift/
  autotargeting 0.90, campaign_state 0.97 (обучение стратегии не отматывается).
  Гейт стоит в plan_bid_modifiers (Э1): неуверенные строки видимы в отчёте
  (`confidence.low_confidence` с p_sign), строки старого формата без rel_error
  применяются как раньше и считаются отдельно (`unknown`). Ноль конверсий
  сегмента = сигнал, а не «неизвестно» (ошибка сверху как одно событие).
  Осталось: rel_error для расписания (часы Метрики) и применение шкалы к
  будущим рычагам (бюджеты, автотаргетинг, вкл/выкл) — пороги уже записаны.
- **Э2.4. Чтение истории.** Квазиэксперименты становятся входом в решения.
  **Сделано для бюджетных скачков (23.08, `sync/agent/history.py`):**
  - Валюта майнинга переехала с `sum_p_pay` (закрыт Э2.0 для агрегатных
    решений) на **цену эффективного лида** — ту же, что у красных линий
    сторожа. Фиктивный интервал «доля от эффекта + запас» заменён
    пуассоновской ошибкой счётчиков лидов четырёх окон DiD; окно без единого
    лида эксперимента не даёт (ноль лидов — сигнал, но не конечный CPL).
  - Читатель сводит эксперименты в **эластичность CPL по бюджету**:
    eps = DiD-эффект / ln(бюджет после/до). eps > 0 — насыщается (предельный
    лид дороже), eps < 0 — есть запас. Знак одинаков для доливов и срезаний.
    Свод — обратновзвешенный по дисперсии: эксперименты → кампания →
    направление; вердикт через шкалу Э2.3 классом budget_shift (0.90).
  - Выход — секция `history` отчёта Э0 и вход кривых насыщения Э3.1. Класс B
    удержан смыслом: DiD чистит сезон, но не причину скачка (трогали
    больное), поэтому это приоритет гипотез, а не приказ двигать деньги.
  **Петля собственных действий замкнута (23.08, сторож):** действие,
  пережившее горизонт без пробоя, закрывается вердиктом «held»
  (observation_closed_at в журнале — раньше такие строки наблюдались вечно,
  а чистый исход не записывался никуда) и уходит в edu_agent_experiments
  строкой source='action', mechanism='before_after'; откатанный пробой —
  строкой verdict='breached'. Класс B, а не A, сознательно: сравнение с
  базой до изменения не вычитает сезон — A появится, когда исход будет
  меряться против заповедника за то же окно. На красном гейте витрины
  закрытие откладывается (той же логикой, что у строк без вердикта);
  в репетиции журнал не трогается (would_close_held в отчёте).

### Точка отсчёта экономики (22.08, прогон 32590373892, зрелое окно до 20.07)

### Э3 — портфельный уровень

- **Э3.1. Кривые насыщения и предельная цена — СДЕЛАНО (23.08,
  `sync/agent/saturation.py`, прогон 32633188555).**
  - Два DiD-источника эластичности (сезон вычтен в обоих): квазиэксперименты
    Э2.4 (314 наблюдений) и **пары соседних недель** против контроля кабинета
    (292 пары; 344 пары поверх уже посчитанного квазиэксперимента отброшены —
    иначе один скачок вошёл бы в свод дважды и фиктивно сузил ошибку).
    Недели только полные и зрелые (воскресенье ≤ границы CRM), обрезанная
    первая неделя окна выбрасывается.
  - Частичный пулинг: свои наблюдения кампании + пул направления без неё
    (leave-one-out); без своих — направление, затем кабинет. Источник
    (`eps_source`) виден в каждой строке.
  - Кривая степенная: лиды = a·бюджет^β, β = 1 − eps (зажим 0.15–1.5 с
    флагом). **Предельная цена эфф. лида = средний CPL / β** на последних
    28 зрелых днях; вдоль кривой ×(S/S₀)^(1−β). Ошибка — пуассон CPL ⊕ σ_β.
  - На бою: 76 кампаний с кривой (152 строки kind=saturation в
    computed_settings), 99 без объёма в свежем окне. Направления: it
    предельный лид **7334 ₽** (средний 5097), med 3507, vpo 3207, other 3044,
    spo 2651 (средний 1943), transfer 2417 — все «насыщается»; ntb 2224
    (eps −0.14, β>1 — возможен запас, 5 наблюдений, неопределённо); dist
    902–1476 ₽ и eps≈0 — дешёвый предельный лид, но см. точку отсчёта: чек
    dist вдвое ниже, сводить лиды с выручкой будет Э3.2.
  - Вердикты сошлись с Э2.4 повсюду, точность выросла (spo σ_eps 0.019
    против 0.025 на одних квазиэкспериментах).

### Э5 — распределение бюджета через бандиты

Thompson sampling вместо A/B: бюджет распределяется пропорционально вероятности объекта
быть лучшим, распределение уточняется само. Не требует значимости и не требует ждать.

## 9. Инварианты

- Ни одно решение не принимается на молчаливых нулях: отсутствие данных и нулевой
  результат обязаны различаться в отчёте прогона (случай `blind_accounts`, `3904bfd`).
- Автоматический выбор, у которого высокая цена ошибки, печатается в отчёт прогона
  (случай `segment_goal_columns`, `06f35f0`).
- Необратимые действия требуют более высокой уверенности, чем обратимые, и никогда не
  принимаются на одной неделе данных.
- Темп обучения = число обратимых решений в неделю. Одна кампания из 83 — это репетиция,
  а не работа.
