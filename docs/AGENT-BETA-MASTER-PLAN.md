# Агент-директолог: единый план до полноценной беты

> **Для исполнителя:** обязательный под-скилл — `superpowers:subagent-driven-development`
> (рекомендуется) или `superpowers:executing-plans`. Шаги размечены `- [ ]`.

**Цель.** Замкнуть полный цикл — анализ → идеи → отбор → действие → замер → новый
анализ — включая сборку и запуск новых кампаний, и снять ограничитель, который
сегодня превращает решения агента в очередь из применённых устаревших расчётов.

**Архитектура.** Один поток действий с двумя общими лимитами (50 действий за прогон,
50 000 ₽ риска в неделю) разбирается на **семь независимых полос**, у каждой своя
физика ошибки, свой срок замера, свой бюджет и свой темп. Поверх полос —
**четыре класса достоверности**: от арифметики, которая не может быть неверной, до
предложения, которое агент применять не вправе. Объём применяемого при этом растёт,
а риск не растёт, потому что деньги под ударом считаются по классу, а не по числу
строк. Генераторы идей питают единый реестр, реестр приоритезирует по «ожидаемая
ценность ÷ цена теста», билдер становится ещё одним рычагом агента.

**Стек.** Python 3.11, psycopg2, pytest, PostgreSQL (Supabase), GitHub Actions.
UI — Next.js 16 в репозитории `d:\vscode\EDU v2` (`components/platform/AgentAdmin.tsx`).

**Спека.** Этот файл сводит и заменяет как план:
- `docs/AGENT-ROADMAP-2026-08-25.md` — Ф5–Ф9 (что остаётся),
- `docs/AGENT-BETA-PROTOCOL.md` — протокол наблюдения за бетой,
- `docs/AGENT-EXPERIMENT-PIPELINE.md` — контур экспериментов,
- `docs/AGENT-AUDIT-2026-08-23.md` — замеры, на которые опираются числа,
- `docs/AGENT-DATA-SOURCES.md` — что источники физически отдают.

## Глобальные инварианты

Требования этого раздела неявно входят в каждую задачу.

- **Защиту нельзя ослабить настройками.** `LOCKED_KEYS` в `sync/agent/config.py`
  остаётся закрытым списком. Новая полоса не имеет права обходить красную линию,
  порог наблюдений, линию обвала расхода (`rollback.SPEND_COLLAPSE_SHARE = 0.30`).
- **Каждая правка — со своим тестом.** Тест пишется до кода, красный прогон
  показывается, зелёный прогон показывается.
- **Удаление объектов запрещено навсегда.** Пауза вместо удаления, allow-лист
  `ALLOWED_ACTION_KINDS`, не блок-лист.
- **Заповедник неприкосновенен.** Ни одно действие ни одной полосы не касается
  кампаний из `edu_agent_holdout`. Без базы сравнения все замеры этого плана —
  самоподтверждение.
- **Ни одного нового кармана денег.** Полоса тратит из уже существующих двух
  источников: разведочный карман расчёта (`portfolio.exploration_bonus`) и
  недельный риск-бюджет движка записи. Полоса, назначающая себе бюджет сама, —
  это дыра, а не полоса.
- **Красный гейт данных останавливает ВСЕ полосы, включая гигиену.** «Ноль
  конверсий за зрелое окно» — утверждение о данных; при красном гейте данные
  не заслуживают доверия, и класс 0 перестаёт быть арифметикой. Исключение
  ровно одно и уже существует: откат по красной линии — он возвращает кабинет
  в известное прошлое состояние и от свежести витрины не зависит.
- **Опечатка — ошибка, а не умолчание.** Неизвестный ключ конфига роняет разбор.
- **У сокращения обязан быть адресат.** `sync/agent/balance.py` остаётся в силе для
  всех полос: такт, который только сжимает, не применяется.
- **Даты:** хранить UTC, показывать Europe/Moscow. Расход Директа уже с НДС.
- **Секреты** — только в `.env` и в секретах Actions.

## Часть 1. Разбор ограничителя — почему очередь это дефект

### 1.1. Три замера

**Замер А (журнал за 30 дней, probe 32957266737).** В журнале встречаются
только три вида действий: `bidmodifier.add` 74 строки, `bidmodifier.set` 24,
`schedule.set` 14 (строка журнала — это не применённое действие: боевых
применений за всё время девять, остальное репетиции и незакрытые). Бюджетных
действий, целевого CPA, минус-фраз, площадок нет **ни одной строки ни в одном
статусе** — до журнала они не доходят вовсе. Причина найдена и
починена коммитом `d36d1c3`: `cap_actions` был срезом `actions[:50]`, а план
собирается рычагами по порядку — корректировок всегда больше 50, и до бюджета
очередь не доходила никогда. Лимит прогона работал как **выбор рычага**, чего
никто не задумывал.

**Замер Б (репетиция Э1 после починки, run 32956479310).** Кап перестал жать
(`actions_left_in_run: 48`), ограничение переехало на риск-бюджет:
`weekly_risk_left_rub: 11 124` из 50 000, `run_risk_left_rub` после первого
кабинета 10.98 ₽, отказов по причине `budget` — 48.

**Замер В (что держит риск-бюджет, probe 32957266737).** Пять корректировок,
применённых **22.08**, держат **38 876 ₽** из 50 000. Это цена по СТАРОЙ модели:
дельта-модель риска (`writer/exposure.py`) появилась 25.08 коммитом `ed84cb0`,
и её собственная шапка называет ровно эту строку — «корректировка AGE_55 −43 %
в кампании 114057545 стоила 38 876 ₽, 78 % недельного лимита за одно касание
сегмента, который берёт несколько процентов расхода». Модель починена, а **журнал
остался в старых ценах**, и `spent_risk` продлевает окно назад на горизонт замера
— то есть старая цена держит бюджет до 05.09.

### 1.2. Что не так с одним общим лимитом

1. **Лимит выбирает не важное, а первое.** Порядок сборки плана — не порядок
   ценности. Пока лимит один на всех, случайность порядка сортировки решает,
   какой рычаг вообще существует.
2. **Отложенное протухает.** Действие посчитано на данных дня X: baseline CPA,
   доля сегмента, красная линия, ожидание. Применённое через три дня — это
   применение вчерашнего расчёта к сегодняшнему кабинету. Очередь не «сохраняет
   решение», она **сохраняет устаревшее решение**.
3. **Сокращение конкурирует с доливкой за один и тот же бюджет риска.** Минус-фраза
   на запрос, который сжёг три CPA при нуле конверсий, **высвобождает** деньги.
   Платить за неё из того же кармана, что за доливку бюджета, — арифметическая
   ошибка: у этих действий противоположный знак риска.
4. **Абсолютное число не масштабируется с кабинетом.** 50 000 ₽/нед при недельном
   расходе ≈ 5,7 млн ₽ (авг: 20,5 млн за 25 дней) — это **0,9 % расхода**. Лимит
   был задан, когда кабинет был другим, и с тех пор не пересматривался.
5. **Отказ «не влез» неотличим от отказа «не надо».** В отчёте они лежат рядом,
   и по нему нельзя понять, агент придержал решение или отверг его.

### 1.3. Решение — семь полос

Полоса — это класс решений с **общей физикой ошибки и общим сроком замера**.
Полосы не конкурируют друг с другом за слоты и за деньги: у каждой свой лимит.

| Полоса | Виды действий | Единица отбора | Срок замера | Чем платит |
|---|---|---|---|---|
| **1. Гигиена** | `negative.add`, `placement.exclude` | вырезанный расход | 3 дня | ничем (высвобождает деньги); лимит — доля вырезаемого расхода кабинета за такт |
| **2. Тонкая настройка** | `bidmodifier.add/set`, `schedule.set` | сегмент кампании | 7 дней | дельта сегмента × горизонт |
| **3. Перераспределение** | `budget.set`, `budget.set_daily`, `tcpa.set` | кампания | 14 дней | дельта лимита × горизонт |
| **4. Отключение** | `campaign.suspend` | кампания | 14 дней | расход кампании × горизонт; ≤1 за прогон |
| **5. Разведка** | любой вид с признаком `exploration` | кампания | 14 дней | разведочный карман `explore_share` |
| **6. Запуск** | `campaign.create`, `campaign.resume` (новые) | новая кампания | 30 дней | стартовый бюджет × срок теста |
| **7. Предложения** | не применяются | — | — | ничем |

**Мастер кампаний — тоже полоса 7.** МК не отдаётся Reports API, но его статистика
и настройки читаются сессионным API — тем же способом, которым сняты аудит и
геомедийка LIME. Значит слепая зона закрывается на ВХОДЕ: 6,2 % расхода перестают
быть «неизвестно чем» и входят в картину кабинета наравне с остальным. Рычага
записи в МК при этом нет и не появится, поэтому всё, что агент про него понял,
выходит рекомендацией человеку, а не действием. Это не ущербный режим: полоса 7
несёт тот же аппарат — ожидание, критерий успеха, срок, — и её исполнение человеком
замыкается в реестре идей (задача 26б) ровно как исполнение любого рычага.

**Почему именно так разделено.** Полосы 3 и 4 Павел назвал явно
(«бюджетные правила отдельно по перераспределению, отключению и запуску»), и это
разделение подтверждается механикой Директа, а не удобством: перераспределение
сохраняет сумму кабинета, отключение меняет состав портфеля, на котором посчитаны
λ и целевые бюджеты **всех остальных** кампаний, запуск вводит объект без истории,
которому ни один замер прошлого не применим. Гигиена отделена, потому что у неё
обратный знак риска. Тонкая настройка отделена от перераспределения, потому что
корректировка сегмента не сбрасывает обучение стратегии, а сдвиг лимита сбрасывает.

### 1.4. Четыре класса достоверности

Полоса отвечает на «что двигаем», класс — на «насколько мы уверены и надо ли
за это платить риском».

| Класс | Что это | Примеры | Право применять | Платит риск |
|---|---|---|---|---|
| **0. Арифметика** | утверждение о прошлом, а не прогноз | минус-фраза на запрос с расходом > 3 CPA и нулём конверсий за зрелое окно; запрет площадки по тому же признаку; сужение гео с нулём конверсий | всегда | нет |
| **1. Измеренное** | своё измерение прошло порог полосы | сдвиг бюджета по кривой насыщения, корректировка сегмента с p ≥ порога | по ступени полосы | да |
| **2. Ставка** | основание есть, измерения нет | разведка, новая кампания из связки, смена цели | из кармана разведки / полосы запуска | да |
| **3. Предложение** | ни измерения, ни рычага | новая посадочная, новый оффер, смысловая гипотеза модели, идея с рынка | никогда | нет |

**Откат через полосы не идёт.** Возврат по красной линии — не решение агента,
а исполнение уже принятого обязательства, и он живёт своим путём
(`writer/rollback.py`, сторож). Ни лимит полосы, ни ступень, ни риск-бюджет его
не касаются: откат, которому не хватило бюджета, — это не откат.

**Класс 0 не платит риск — это не послабление, а исправление арифметики.**
Такое действие не ставит деньги под удар, оно снимает их с огня. Цена его ошибки —
упущенная выгода на трафике, который за зрелое окно не дал ни одной конверсии
при расходе выше трёх CPA. Это не ноль, но это и не «весь расход кампании».
Считать её будет `exposure.cut_exposure` (задача 8), и у полосы 1 остаётся свой
ограничитель — **доля вырезаемого расхода за такт**, чтобы сломанные данные не
вырезали кабинет целиком за один проход.

**Прямой ответ на «если все 400 рекомендаций хорошие, почему мы их не вносим».**
После разделения: все рекомендации класса 0 вносятся **все и сразу**, без очереди
и без риск-бюджета. Именно они составляют большинство того, что генерится, и
именно они сегодня стоят в очереди позади корректировок. Рекомендации класса 1
вносятся по ступени полосы. Класс 2 — из кармана разведки. Класс 3 уходит человеку.

### 1.5. Лестница риска — вместо угадывания числа

Вопрос «какой поставить недельный лимит» не имеет ответа до беты: мы не знаем
долю попаданий. Поэтому лимит не назначается, а **зарабатывается**.

Риск-бюджет полосы задаётся **долей недельного расхода кабинета**, а не абсолютом
(дефект 1.2.4), и ходит по ступеням:

| Ступень | Доля недельного расхода | Условие перехода вверх |
|---|---|---|
| 0 — тень | 0 % (пишет «сделал бы», не делая) | **только решением человека** — см. ниже |
| 1 — проба | 1 % | ≥ 12 закрытых наблюдений, доля улучшений ≥ 60 % |
| 2 — рабочая | 3 % | ≥ 24 закрытых, ≥ 60 %, деньги подтвердили на втором чекпоинте ≥ 50 % успехов |
| 3 — полная | 6 % | ≥ 48 закрытых, ≥ 65 %, второй чекпоинт ≥ 60 % |

Переход **вниз** — на ступень, немедленно: доля улучшений < 40 % на последних 12
закрытых, или сработала линия обвала расхода, или откат не исполнился.

**Из тени лестница не выводит — выводит человек.** Ступень 0 не даёт применять,
значит закрытых наблюдений на ней не появится никогда, и автоматический переход
0 → 1 логически невозможен: полоса в тени заперта навсегда. Поэтому тень — это
не низшая ступень лестницы, а **режим приёмки нового рычага**: агент две недели
пишет «сделал бы X, жду Y к дате D», человек читает совпадения на экране и
решает, выпускать ли рычаг. Дальше, со ступени 1, лестница работает сама.

В тень попадают только рычаги, чья ошибка не откатывается полностью:
отключение кампании (остановленная автостратегия теряет обучение), запуск новой
(стартовый бюджет уже потрачен к первому вердикту), смена цели и стратегии.
Рычаги с историей — корректировки, расписание, минус-фразы, площадки, бюджет —
стартуют со ступени, которую им даёт их собственный track record, а не с нуля.

При недельном расходе ≈ 5,7 млн ₽ ступень 1 даёт 57 тыс ₽ на полосу — примерно
сегодняшний общий лимит, но **на каждую полосу отдельно** и с правом расти.
Ступень 3 даёт 342 тыс ₽.

Худший случай считаем явно. Риск-долю платят четыре полосы: тонкая настройка,
перераспределение, отключение, запуск (гигиена не платит по построению, разведка
платит из бюджетного кармана, предложения не применяются). Все четыре на ступени
3 — это 24 % недельного расхода под непроверенными изменениями. Если КАЖДОЕ из
них окажется вредным и ни одно не откатится, потеря — 24 % недели, то есть
**5,5 % месячного расхода**. При ROMI 1.9 это примерно 10–11 % месячной прибыли:
цена одной плохой недели в сезон. Верхняя ступень достижима не раньше, чем у
всех четырёх полос наберётся по 48 закрытых наблюдений с долей улучшений ≥ 65 %,
то есть по факту не в бету.

**Решение Павла (одно):** какие рычаги выпускать из тени и когда. Рекомендация на
старт беты — полосы 1, 2, 3 работают со ступени, которую даёт их track record
(у корректировок и расписания он уже есть, у бюджета почти нет — значит ступень 1);
полосы 4 (отключение) и 6 (запуск) стоят в тени и выходят из неё решением Павла
после того, как экран покажет совпадение намерений с фактом. Никакого «через две
недели автоматически» — из тени выводит только человек.

### 1.6. Судьба «отложенного»

Статус `deferred` исчезает как понятие. Действие, не прошедшее лимит полосы,
становится **отказом с причиной** `lane_limit` и пересчитывается следующим тактом
заново — на свежих данных, со свежей красной линией.

Взамен в отчёт входит **дефицит полосы**: «полоса 3: заявлено 48 действий на
921 690 ₽, лимит полосы 57 000 ₽, пропущено 3, отказано 45; при текущей ступени
полоса пропускает 6 % своих решений». Это число — не жалоба, а вход для решения
о ступени.

**Повторный дефицит эскалируется человеку.** Пересчёт каждый такт снимает
проблему устаревших решений, но сам по себе создаёт новую: одно и то же
действие может отказываться тридцать тактов подряд и молча. Поэтому объект,
отказанный по `lane_limit` **пять тактов подряд**, попадает в предложения
человеку отдельной строкой: «сдвиг бюджета кампании X на 40 000 ₽ не проходит
лимит полосы пятый такт — либо ступень мала, либо решение неверно». Именно это
и есть «либо делаем, либо не делаем»: третьего состояния — молчаливого
висяка — в системе нет.

#### Задача 1: Переоценка журнала под дельта-модель

**Файлы:**
- Создать: `sync/agent/writer/reprice.py`
- Создать: `scripts/reprice_actions.py`
- Тест: `tests/test_agent_writer_reprice.py`

**Откуда берётся доля сегмента.** Блока `exposure` в журнале НЕТ: `INSERT_ACTION_SQL`
пишет `payload`, `direct_type`, `setting_key`, `risk_basis`, `baseline_daily_rub`, но
не сам `exposure`. Пересчёт «по правилу неизвестной доли» дал бы ту же старую цену
(доля неизвестна → под ударом весь объект), то есть ничего бы не изменил.

Доля восстанавливается из расчёта Э0 **на дату действия**:
`edu_agent_computed_settings` хранит строки с `calc_date`, `setting_kind`,
`setting_key`, `support_n`, а доля считается тем же `writer/plan.segment_shares`,
что и при первичной оценке. Ключ соединения — `(direct_type, setting_key)` строки
журнала. Это не приближение и не догадка: та же формула на тех же данных, только
взятых из истории, а не из памяти прогона.

Строка, для которой доля не нашлась (расчёт того дня не сохранился, вид действия
доли не имеет), **не переоценивается** и уходит в отдельный список отчёта.
Молчаливое «оставили как есть» неотличимо от «проверили и всё верно».

**Интерфейсы:**
- Потребляет: `writer/plan.segment_shares`, `writer/exposure.daily_rub`,
  `writer/risk.{object_daily_cost, action_risk}`, `agent_db` (чтение
  `edu_agent_computed_settings` на дату)
- Отдаёт: `reprice.share_for(action, computed_on_date) -> Optional[float]`,

#### Задача 8: Цена действия по знаку и по нетто

Два дефекта арифметики риска, из-за которых лимит полосы жмёт вдвое сильнее,
чем должен.

**Дефект 8а — вырезающее действие платит как тратящее.** Минус-фраза
высвобождает деньги; её цена — упущенная выгода, а не расход.

**Дефект 8б — перераспределение платит дважды.** Перенос 100 000 ₽ с кампании
A на кампанию B сегодня стоит риском обе дельты: и −100 000 у A, и +100 000
у B. Но под ударом здесь не 200 000 ₽ и даже не 100 000 — под ударом **разница
в эффективности A и B на горизонте замера**. Если мы ошиблись и A была лучше,
потеря равна перенесённой сумме, умноженной на разрыв окупаемостей, а не самой
сумме. Замер Б показывает цену этого дефекта прямо: полоса перераспределения
заявила 921 690 ₽ риска на 48 действиях — это 16 % недельного расхода кабинета
за одну неделю переносов, при том что сумма кабинета не изменилась ни на рубль.

#### Задача 14: Генератор A/B-тестов

**Файлы:** создать `sync/agent/ideas/abtests.py`; тест `tests/test_agent_ideas_abtests.py`

Каталог типов теста × кампания-кандидат. Каталог явный и закрытый:

| Тип теста | Рычаг | Сбрасывает обучение |
|---|---|---|
| ставка/бюджет вверх | `budget.set` | да, если больше `BUDGET_SAFE_DELTA` |
| ставка/бюджет вниз | `budget.set` | так же |
| цель CPA | `tcpa.set` | да |
| **смена цели оптимизации** | `goal.set` (задача 21) | да |
| **смена стратегии** | `strategy.set` (задача 22) | да |
| расписание | `schedule.set` | СЧИТАЕТСЯ ДА |
| **аудитории и ретаргетинг** | `audience.add` (задача 23) | нет |
| **гео** | `geo.set` (задача 24) | нет |
| площадки | `placement.exclude` | нет |
| тексты и креативы | наряд билдеру | нет |

**Три поправки, внесённые при реализации 27.08** (черновик таблицы выше
оставлен как есть, кроме строки расписания):

1. **Расписание считается сбрасывающим.** `writer/learning.py` относит
   `schedule.set` к «unknown»: временного таргетинга в списке справки нет, но
   объём показов он меняет, и записать его в безопасные значило бы выдать
   незнание за знание. Класс каждого типа генератор СПРАШИВАЕТ у модуля
   рычагов, а не объявляет рядом с типом, — иначе таблица и правило кабинета
   разъедутся молча.

2. **Идеи тестов — класс 3, а не ставки.** Нагрузку теста (лимит, цель CPA,
   расписание) строит только такт записи и только от живого состояния
   кабинета: `budget.diff_budget` требует `fetch_budget_state`. Расчётный
   такт собрать её не может, не соврав о текущем состоянии, — тот же довод,
   по которому генератор `proven` ставит только `bidmodifier.add`. Идея
   несёт рычаг, направление и шаг изменения в `detail.change`, а нагрузку
   получит, когда появится механизм построения нагрузки в такте записи.

3. **Прибавка лимита — только при связывающем лимите.** Замер августа 2026:
   лимит связывал расход у 9 кампаний из 62; остальным прибавка не меняет
   ничего, и рычаг её потом отвергнет (`budget.NOT_APPLICABLE_UP_REASON`).
   Поле `limit_binds` трёхзначное: ключа нет — состояние кабинета не снято,
   `False` — не связывает, `True` — связывает. Поле «сколько дней назад
   сбрасывалось обучение» названо `days_since_learning_reset`, а не
   `days_since_budget_change`: сбрасывает обучение не только бюджет.

* **Паспорт выбирается по НАПРАВЛЕНИЮ кампаний фразы, а не по кабинету.**
  `semantic.group_by_direction` разводит кандидатов по `direction_by_campaign`
  (он уже есть в прогоне), и каждая группа уходит своим батчем со своим
  паспортом. Фраза, откручивавшаяся в кампаниях РАЗНЫХ направлений, паспорта
  не получает вовсе: паспорта соседей противоречат друг другу ровно там, где
  это опаснее всего — «после 9 класса» у высшего анти-маркер, у СПО целевой
  маркер, и любой из двух судил бы фразу чужим продуктом.
* **Промпт пересобран под кэш.** Формат ответа стоял ПОСЛЕ списка фраз, то
  есть после единственной изменчивой части: каждый батч сдвигал его и обнулял
  общий префикс. Теперь всё стабильное (роль, описание, паспорт, правила,
  формат) идёт до метки `PHRASES_MARKER`, фразы — только после неё; тест
  сравнивает префиксы двух разных батчей посимвольно.
* **`SEMANTIC_CONTEXT` переехал в слой** (`semantic.DEFAULT_CONTEXT`). Две
  строки об одном продукте в разных файлах разъезжаются молча.
* **В промпт едет проекция, а не паспорт.** Полный — 27 КБ, окно модели
  этого не выдержит: список фраз вытеснился бы и батч вернулся бы пустым.
  Проекция — шесть разделов, которыми решается интент фразы (`PASSPORT_BUDGET`
  = 2400 символов, тест на длинном паспорте). Анти-маркеры едут С ПРИЧИНОЙ:
  «аспирантура» без пояснения читается как «слово запрещено», а нужно «это
  другой продукт кабинета».
* **Перечень направлений стал закрытым** (`classify.DIRECTIONS`) и сверяется
  тестом с литералами, которые возвращает `detect_direction`: паспорт под
  ключом, которого прогон не спросит, не применялся бы молча.
* **Доставка паспорта — файлами в репозитории агента**
  (`sync/agent/passports/<направление>.json`, импорт
  `scripts/import_passport.py`). Прогон Э0 идёт в GitHub Actions на чекауте
  edu-sync, репозитория билдера там нет. Копия версионируется и несёт в себе
  источник и дату импорта, чтобы не стареть молча.
* **Залит один паспорт — `school`.** Он единственный, чьё направление
  однозначно: `detect_direction` проверяет школу первой. `dist` смешивает
  ВПО- и СПО-дистант (в него уходит любое имя со словом «дистанц/заоч/онлайн»),
  одним паспортом не описывается, и скрипт отказывает без `--force`. Остальные
  направления работают на общем описании — доля размеченных с паспортом фраз
  видна в отчёте прогона (`semantic.passports`).
