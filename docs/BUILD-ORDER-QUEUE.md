# Очередь нарядов билдеру — контракт обмена

Форму САМОГО наряда описывает `docs/BUILD-ORDER-CONTRACT.md`. Здесь — как
наряд доезжает до исполнителя и как исход возвращается обратно: таблица
очереди, статусы, форма ответа и что агент делает с ответом.

| | |
|---|---|
| Пишет и читает | `edu-sync` → `sync/agent/build_queue.py` |
| Читает и отвечает | «EDU кампании» (`d:\vscode\EDU`) → отдельная задача |
| Таблица | `edu_agent_build_orders` (миграция `migrations/edu/20260829_agent_build_orders.sql`) |
| Точка входа для билдера | `scripts/agent_build_queue.py` |
| Тест отправителя | `tests/test_agent_build_queue.py` |

Сторона билдера в этой задаче НЕ трогалась намеренно: контракт объявлен до
того, как обе стороны его реализуют, — иначе первый же наряд проверял бы
догадку одного репозитория о другом. Подключение билдера — отдельная задача,
и её приёмка — тест НА СТОРОНЕ БИЛДЕРА, который читает эту таблицу.

## Зачем очередь вообще

Наряд — единственный способ агента завести кампанию: все прочие его рычаги
правят существующий объект. `campaign.create` вне allow-листа записи не по
недосмотру — из `edu-sync` такой запрос невыразим в принципе: у агента нет ни
групп, ни ключей, ни текстов (`writer/guardrails.BUILDER_REASON`).

Без обратной связи вынос остаётся предложением на экране, а не циклом: агент
не знает ни `campaign_id` созданной кампании, ни дня, с которого её можно
мерить, — значит не может ни наблюдать её, ни откатить.

## Строка наряда: что кладёт агент

```
order_id      TEXT PRIMARY KEY   -- 'consolidate-vpo', без даты
idea_id       TEXT               -- обратный адрес в реестр идей
account       TEXT NOT NULL      -- логин кабинета
kind          TEXT NOT NULL      -- consolidate | rebuild | expand
level_slug    TEXT NOT NULL      -- имя папки уровня на диске билдера
campaign_name TEXT NOT NULL      -- имя кампании в Директе, несёт order_id
direction     TEXT
status        TEXT NOT NULL      -- queued | taken | built | failed | cancelled
status_reason TEXT
order_json    JSONB NOT NULL     -- ПРОВЕРЕННОЕ тело наряда
campaign_id   TEXT               -- ответ билдера
started_on    DATE               -- ответ билдера
experiment_id TEXT               -- наблюдение, заведённое агентом
queued_at     TIMESTAMPTZ
updated_at    TIMESTAMPTZ
```

`order_json` — не исходный словарь генератора, а результат
`build_order.validate`: с нормализованными фразами и проверенной
кросс-минусовкой. Билдер обязан собирать ровно то, что проверил валидатор,
иначе проверка была о другом тексте.

## Статусы и кто их двигает

```
queued ──take──► taken ──accept──► built ──accept──► built
   │                │                (дозаполнение started_on)
   │                └──fail──► failed ──requeue──► queued
   └──fail/cancel──►
```

| Переход | Кто | Что означает |
|---|---|---|
| `→ queued` | агент | наряд поставлен или обновлён генератором |
| `queued → taken` | билдер | взял в работу; **тело наряда заморожено** |
| `taken → built` | билдер | собрал, вернул `campaign_id` |
| `built → built` | билдер | дозаполнил `started_on`, когда кампанию включили |
| `→ failed` | билдер | не смог; причина обязательна |
| `failed → queued` | человек | причину устранили, наряд возвращается |
| `→ cancelled` | агент/человек | наряд снят до сборки |

**Тело обновляется только в `queued`.** Состав фраз плавает от прогона к
прогону (нагрузка идеи — обновляемое поле), и билдеру обязан достаться
последний. Но как только он наряд взял, обновление стало бы сборкой движущейся
цели: половина кампании собрана по одному составу фраз, кросс-минусовка
доноров — по другому. Попытка переписать взятый наряд — исключение
(`build_queue.OrderFrozen`), а не тихое сохранение прежнего.

**Закрытый наряд свежей постановкой не воскресает.** Статусом распоряжается
ответ билдера и решение человека, а не очередной прогон генератора.

## Ответ билдера

```json
{
  "order_id": "consolidate-vpo",
  "result": "built",
  "campaign_id": "555",
  "started_on": "2026-09-03",
  "note": "залито, кампания на паузе до 03.09"
}
```

**`campaign_id` обязателен для `built`.** Ответ без адреса объекта — это не
«собрал», а «что-то произошло»: наблюдать нечего, откатывать нечего. Такой
ответ едет как `failed`, и разница видна в статусе, а не в комментарии.

**`started_on` — день ПЕРВОЙ ОТКРУТКИ, а не создания.** Кампания создаётся на
паузе (наряд везёт `state: SUSPENDED`, и билдер шлёт `campaigns.suspend` сразу
после `campaigns.add`), между созданием и включением стоит человек. Окно
наблюдения, отсчитанное от дня создания, съело бы горизонт днями простоя, и
вердикт «не окупился» вынесла бы пауза, а не кампания.

`started_on` можно не присылать: `null` означает «собрана, но ещё не
включена» — законное состояние. Наблюдение по такому ответу не заводится;
второй ответ с датой его заведёт.

Отказ:

```json
{"order_id": "consolidate-vpo", "result": "failed",
 "reason": "паспорт продукта не покрывает направление: оговорки не проверить"}
```

Причина обязательна: наряд, закрывшийся молча, неотличим от наряда, до
которого не дошли руки, и следующий прогон поставил бы его заново, не зная,
что уже спрашивал.

## Чем ходить в очередь

Билдеру не нужен свой SQL по этой таблице, и это не удобство, а граница:
законность перехода статуса, заморозка тела взятого наряда и заведение
наблюдения обязаны жить в ОДНОМ месте. Последнее вообще не про билдера — он
про кампанию знает клики и расход, а вердикт по горизонту считает агент.

```
python scripts/agent_build_queue.py list
python scripts/agent_build_queue.py take consolidate-vpo --by builder
python scripts/agent_build_queue.py accept consolidate-vpo --campaign-id 555 \
    --started-on 2026-09-03
python scripts/agent_build_queue.py fail consolidate-vpo --reason "..."
```

Каждая команда печатает строку наряда после перехода — тем же JSON-ом, что
лежит в базе. Незаконный переход и ответ без обязательного поля — ненулевой
код возврата и исключение с причиной, а не тихое сохранение прежнего.

## Что агент делает с ответом

`build_queue.accept` заводит НАБЛЮДЕНИЕ — строку в `edu_agent_experiments`:

| Поле | Значение | Почему так |
|---|---|---|
| `experiment_id` | из ключа действия запуска | тем же ключом легло бы действие в журнал записи, стань `campaign.create` применимым: замысел и исход — один объект, а не два документа |
| `object_id` | `campaign_id` из ответа | объект наконец существует; до ответа адресовать было нечем |
| `mechanism` | `vs_holdout` | своей истории у новой кампании нет вовсе — «до и после» физически невозможно, разность разностей не из чего собрать. Контроль один: заповедник (`holdout.py`), тот же, которым меряется такт целиком |
| `reliability_class` | `B` | контроль есть, но кампания попала в опыт решением агента, а не жребием. Назвать это `A` значило бы завысить доверие к вердикту |
| `metric` | из `success_rule` наряда | критерий объявлен заранее и уехал билдеру вместе с кампанией; судить другой мерой — оценивать задним числом |
| `started_on` | день открутки из ответа | см. выше |
| `horizon_days` | из наряда | срок назначен под порог значимости (`power.MIN_EXPECTED_PAYMENTS`) |
| `stake_rub` | недельный лимит / 7 × горизонт | деньги под ударом за срок замера |
| `stake_source` | `donor_spend_moved` | **не третий карман.** Недельный лимит равен тому, что доноры по этим фразам уже тратят (`launch.campaign_from_donors` считает его из измеренного расхода): деньги переезжают, а не назначаются |

Исход по горизонту считает `ideas/feedback_out.report` — тем критерием,
который выписан в наряде, — и возвращает билдеру вместе с сырыми поисковыми
запросами для его дообучения (`docs/examples/launch-feedback-consolidate.json`).

## Доступ

Таблица под RLS с нулём политик (`sync/db.enable_rls_for_ddl`): гранты
`anon`/`authenticated` в проекте полные, и доступ держит только row level
security. Синк и билдер ходят ролью `postgres` — она владелец и RLS обходит.
Билдеру не нужен ни сервисный ключ Supabase, ни отдельная роль: ему нужен тот
же `DATABASE_URL`.

## Что осталось за границей задачи

* Сторона билдера — чтение очереди, ответ, идемпотентность заливки по имени
  кампании. Отдельная задача, приёмка — тест в его репозитории.
* Миграция в прод **не применена**: заведение таблицы — решение владельца.
  DDL продублирован в `sync/agent/db.AGENT_DDL`, поэтому первый же прогон
  расчёта заведёт таблицу сам, как и остальные таблицы агента.
